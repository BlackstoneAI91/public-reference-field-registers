## Why a queue counter label needs its own register

A public queue counter label looks like a small piece of signage, but it carries a lot of weight. It tells a visitor where to stand, what the counter handles and what to do next. When the label exists in two languages, the two versions are read side by side by people who may understand only one of them. If the versions drift apart, the visitor who reads the second language gets a different instruction from the visitor who reads the first.

Most premises managers already keep some record of signage changes, but that record is often a folder of drafts, a chat thread and a printed proof with handwriting on it. None of those reliably answers the question a new staff member will ask six months later: which wording was approved, who checked the translation, and when is it due for review?

A language review register is a small, deliberate answer to that question. It is not a translation service and it does not certify anything. It is a log that ties each public label to an approved source wording, a corresponding translation, a named language reviewer, a notice version and a follow-up date. The register is useful wherever a queue counter sits inside a wider queue management system, because the label is the part of that system the public actually reads.

This guide is written for premises managers in Sarawak planning ordinary security and front-of-house projects. It treats the register as a documentation habit, not a technical control. Nothing here replaces a qualified translator or your own approval process.

## The five fields that do the real work

A register can have as many columns as you like, but five fields carry most of the value. Keep them in this order so the record reads left to right as a story.

Approved source wording. This is the exact text that has been signed off in the primary language. Record it character for character, including punctuation and capitalisation. Do not paraphrase it in the register, because the register is the reference, not a summary.

Corresponding translation. This is the reviewed text in the second language. It should sit directly beside the source wording so a reader can compare them without opening another file. If the translation is still a draft, say so in the field rather than leaving it blank.

Language reviewer. Name the person who checked the translation, and note what they checked. A reviewer who confirms meaning is doing a different job from a reviewer who confirms tone and register. Recording which one happened prevents a later reader from assuming more than was done.

Notice version. Give each label a simple version marker, such as a number and a date. When the wording changes, the version changes. This is what lets you tell an old printed label from a current one during a walk-through.

Follow-up date. Set a date when the label should be looked at again, or when a pending translation should be confirmed. A follow-up date turns a static record into something that comes back to you.

Two optional fields are worth adding if your site is busy: the location of the label, and a short note on what triggered the last change. Both help when several counters carry similar wording.

## A fictional worked example: fixed counter name, changing description

Consider a fictional venue in Sarawak with a public service counter. The counter name is fixed: it has been the same for years, appears on the building directory and is spoken by staff. The description underneath it, which explains what the counter handles, changes when the venue reorganises its services.

In the register, the counter name row might read: source wording fixed as the existing counter name, translation fixed as the existing translated name, reviewer recorded as the person who confirmed the name is unchanged, version left at the current marker, follow-up date set for the next annual signage check. Because nothing changed, the row is short and calm.

The description row is where the work happens. The source wording changes from an older description to a new one. The corresponding translation is drafted, then reviewed by a language reviewer who confirms it carries the same meaning and the same level of formality. The notice version moves up, and the follow-up date is set to the day the new printed label is expected to be in place, so someone checks that the printed version matches the register.

The value of separating the two rows is that the fixed name is protected. A reviewer working on the description cannot accidentally alter the name, because the name has its own row and its own note saying it is unchanged. When the venue later adds a second counter, the same pattern repeats: fixed names stay fixed, descriptions carry the version history.

This example is illustrative only. It is not a description of any real venue, and it does not imply that any particular wording is correct for your site.

## How the register fits alongside a queue management system

A queue management system usually has several visible parts: the counter label, the ticket or number display, the waiting area signage and whatever staff use to call the next person. The language review register covers only the written public copy, but it should be cross-referenced with the rest of the system so the wording stays consistent.

A practical habit is to give each public text element a short identifier and record it in the same register, even if the review depth differs. Counter labels get the full five fields. A short directional sign might need only source wording, translation and version. The register then becomes a single index of public copy rather than a file about one label.

When the venue plans a change to its queue management system, the register gives the project a checklist of copy that will be affected. That is useful during planning conversations, because copy changes are easy to overlook when the focus is on the physical setup. ## Reviewer roles and what each one signs off

A common failure in two-language signage is that nobody is clearly responsible for the second language. The register fixes this by naming a language reviewer per row, but it helps to distinguish the roles involved.

The approver owns the source wording. They decide what the counter is called and what the description says. They are usually a manager or supervisor close to the service.

The language reviewer checks the translation against the approved source wording. Their sign-off means the translation says the same thing, not that the service is correct. Record the date of their check.

The signage coordinator, often a facilities or admin role, owns the version marker and the follow-up date. They make sure the printed label matches the register and that old versions are removed.

A fourth role, the reader, is worth keeping in mind even though they never sign the register. If a visitor cannot tell from the label which counter to approach, the register has recorded a process but not solved a problem. A short walk-through with a colleague who reads the second language is a cheap way to test whether the label works.

For sites that also manage door access for staff areas, the same principle of naming roles appears in access planning: smart locks work best when the door condition, user roles and backup method are reviewed before installation, and for business use the choice between a standalone smart lock and an access-control panel is usually checked first. The parallel is deliberate: named roles and a recorded review beat an informal understanding.

## Version markers and follow-up dates in practice

Version markers only help if they are used consistently. Pick one format and write it down in the register header. A simple number plus the date of approval is enough for most sites. Avoid reusing a version number after a correction; move forward instead, so the history stays readable.

Follow-up dates serve two purposes. The first is to catch pending work, such as a translation awaiting review. The second is to prompt a periodic check of labels that have not changed. A twelve-month cycle is a reasonable starting point for a low-change counter, but treat that as an example rather than a rule; a counter whose services change often may need a shorter cycle, and a stable one may need less.

When a follow-up date arrives, the check is short: does the printed label match the register, is the translation still accurate, and has anything about the counter changed? Record the outcome even when nothing changed, because a dated note saying no change is itself useful evidence of attention.

If a label is replaced, mark the old version as retired rather than deleting the row. Deletion loses the history that makes the register trustworthy.

## Common pitfalls and a short checklist

Several small mistakes undermine a register more than any single large one.

Paraphrasing the source wording. The register must hold the exact approved text, or comparisons become guesswork.

Leaving the reviewer field blank. An unnamed review is indistinguishable from no review.

Letting the translation drift without a version change. If the second language changes, the version changes too.

Treating the register as a one-time document. A register with no follow-up dates is a snapshot, not a process.

Mixing languages in one field. Keep source and translation in separate columns so each can be read on its own.

A short checklist for a new row, offered as an author heuristic rather than a standard: source wording copied exactly; translation present or marked as pending; reviewer named with the scope of their check; version marker applied; follow-up date set; location noted. Six ticks is a reasonable target for a counter label.

For premises managers planning broader front-of-house work, the register is one small document among several. If your project includes security systems, a site survey and camera placement are typically part of the planning conversation, and those discussions also benefit from a written record of what was agreed. The language register and the project record are different documents with the same underlying habit: write down what was approved, who approved it and when it should be looked at again.

## Where to start this week

Start with one counter. Open a simple table with the five core fields and one row for the counter name and one for the description. Copy the current approved wording exactly, note the current translation, name the person who last checked it if you know, apply a version marker and set a follow-up date.

Then walk to the counter and compare the printed label with the row. Any difference is the first thing the register has caught. Fix the label or the row, record which, and move on.
