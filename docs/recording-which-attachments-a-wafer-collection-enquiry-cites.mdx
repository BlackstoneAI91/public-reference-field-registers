## Why an attachment register earns its place in a scrap enquiry

A wafer scrap collection enquiry rarely travels as a single document. It arrives as a bundle: a covering note, a list of what is being offered, a reference to an earlier exchange, and often a file that someone renamed on the way to the shared drive. By the time the enquiry reaches a procurement reviewer in Singapore, the folder may hold three versions of the same note and no clear statement of which one is current.

An attachment register is a small administrative control that fixes this. It is not a technical assessment, a valuation or a commitment to collect anything. It is a table that records, for each attachment in the enquiry, what the file is called, what it appears to be, which version is current, and whether anything referenced is missing. The register gives the reviewer a single place to check before replying, and it gives the next person who opens the folder a record of what was decided and why.

This guide is written for Singapore procurement teams who source, receive and document semiconductor and solar materials. It stays deliberately on the administrative side: labelling, versioning and reconciliation. It does not cover material handling, technical processing, pricing or transport arrangements, and it does not tell you what a supplier should do with the material. Those questions belong in the enquiry itself and in the supplier's own response.

## What the register should and should not contain

Keep the register narrow. A useful attachment register answers four questions for each file: what is it called, what does it appear to be, is it the current version, and is it present. Anything beyond that tends to turn the register into a second copy of the enquiry, which defeats the purpose.

Columns that work well in practice include: a row number, the attachment label exactly as it appears in the enquiry, the file name as received, a short description in your own words, the version or date shown on the document, a status (current, superseded, missing, unclear), the date you checked it, and a note on what action is needed. A final column for the person responsible keeps the register from becoming an orphan document.

Leave out material that does not belong in a shared administrative record. Do not paste personal contact details, private correspondence, commercial terms or anything marked internal or restricted into the register. If an attachment itself contains such material, record only that the attachment exists and its status; do not reproduce its contents. The register is a map of the bundle, not the bundle.

One practical habit helps: record the attachment label exactly as the sender wrote it, even if it is inconsistent or misspelled. The label is the only reliable key for matching what the sender meant to what you received. You can add a cleaned-up description in a separate column, but keep the original label intact so that a later reader can trace the match.

## A copyable register layout

The table below is a starting template. Copy the column headings into a spreadsheet and add one row per attachment. The example rows are illustrative only; they describe a fictional Singapore buyer's enquiry and are not drawn from any real transaction.

Row 1. Label: "Cover note – scrap offer". File name: cover-note-v2.pdf. Description: covering note for the enquiry. Version shown: dated 12 March. Status: current. Checked: 14 March. Action: none. Owner: procurement lead.

Row 2. Label: "Material list (rev A)". File name: material-list-revA.xlsx. Description: list of offered material referenced in the cover note. Version shown: rev A. Status: superseded. Checked: 14 March. Action: confirm whether rev B exists; keep rev A on file. Owner: procurement lead.

Row 3. Label: "Earlier note – see attached". File name: (none received). Description: a note referenced in the cover note but not included in the bundle. Version shown: unknown. Status: missing. Checked: 14 March. Action: request the missing reference from the sender; do not delete the reference to it. Owner: procurement lead.

Row 4. Label: "Reference sheet". File name: reference-sheet.pdf. Description: a reference sheet attached to the enquiry. Version shown: undated. Status: unclear. Checked: 14 March. Action: ask the sender to confirm the version date. Owner: documentation officer.

Four rows are usually enough to expose the common problems: a current document, a superseded one, a missing one and an unclear one. The register does not resolve those problems; it makes them visible so that someone can.

## Reading the three example statuses

The three statuses in the template do different work, and it helps to keep them distinct.

A current reference is the version you intend to rely on for the enquiry. Mark it current only when the document itself shows a version or date that matches the latest one you have seen, or when the sender has confirmed it in writing. Do not mark a file current simply because it arrived last; arrival order is not version order.

A superseded note is an earlier version that has been replaced. Keep it. Deleting a superseded note removes the trail that explains why the current version differs, and a later reviewer may need that trail. Mark it superseded, note the version it was replaced by, and leave it in the folder. The register row is the pointer that stops someone reopening the old note by mistake.

An attachment identified but missing is the most useful row of all. The cover note refers to something that did not arrive, and without a register row the gap is invisible. Record the label exactly as it was written, mark it missing, and note that the reference must be preserved. The missing row is not a failure of the register; it is the register doing its job.

An unclear status is a holding position. Use it when a document has no visible version or date, or when two files appear to describe the same thing. Unclear is honest; it tells the next reader that a question is open rather than settled.

## Asking for the missing reference without losing the old one

When a row is marked missing, the next step is a short, specific request to the sender. The request should name the attachment label exactly as it appeared, state that it was not received, and ask for the version the sender intended. Keep the request administrative: you are asking for a document, not commenting on the material or the commercial position.

A workable pattern is: "Your cover note refers to an earlier note under the label [exact label]. That attachment was not included in the bundle we received. Could you send the version you intended us to read, and confirm its date?" That wording does three things. It quotes the label so the sender can match it, it states the fact of non-receipt without blame, and it asks for a date so the register can move the row from missing to current or superseded.

While the request is open, preserve the old reference. Do not overwrite the missing row with the new file when it arrives; add a new row for the received document and cross-reference the original row. That way the register shows both the gap and its resolution. If the sender replies that the referenced note no longer exists, record that reply against the original row and close it as withdrawn rather than deleting it.

The same discipline applies to a superseded note. When a replacement arrives, add a row for it, mark the earlier row superseded, and note which row replaced it. The register then reads as a short history rather than a snapshot, which is what a later reviewer actually needs.

## Keeping the register aligned with the enquiry

An attachment register is only useful if it matches the enquiry it describes. Two habits keep the two aligned.

First, date every check. A register row without a check date cannot tell a later reader whether the status was verified last week or last quarter. A simple checked-on column, filled in each time someone opens the bundle, turns the register into a light audit trail without adding much effort.

Second, reconcile before you reply. Before sending any response to the enquiry, read the register against the folder one more time. Confirm that every current row still has its file, that every missing row is still missing or has been resolved, and that no new attachment has arrived without a row. This final pass takes a few minutes and catches the common case where a file was added to the folder but never registered.

Where the enquiry concerns silicon recovery, the register may need to distinguish between attachments that describe the offered material and attachments that are simply correspondence. ## A short checklist before the enquiry leaves your desk

The checklist below is an author's heuristic, not an established standard. Treat the items as prompts and adapt them to your team's own practice.

One: every attachment in the bundle has a row, and every row has a file or a missing status. Two: the attachment label is recorded exactly as the sender wrote it. Three: each row has a status of current, superseded, missing or unclear, and no row is left blank. Four: each row has a checked-on date. Five: superseded rows name the row that replaced them. Six: missing rows have an open request recorded against them. Seven: no personal contact details, commercial terms or restricted material appear in the register. Eight: the register has a named owner.

A register that passes these eight prompts is ready to sit alongside the enquiry. It will not answer the sourcing question, and it is not meant to. Its value is that the next person who opens the folder can see, at a glance, what arrived, what is current, what is missing and who is dealing with it.
